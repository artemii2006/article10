# GBRT yield-only для `xr_2y`: журнал экспериментов

## Цель проекта

Мы пытаемся максимально воспроизвести результат статьи *Bond Risk Premia with Machine Learning* для yield-only GBRT по целевой переменной `xr_2y`. Итоговая задача — не просто найти комбинацию с минимальным validation MSE, а получить корректную полную репликацию:

1. повторить структуру данных и преобразования авторов;
2. корректно сформировать годовой holding-period excess return;
3. реализовать ежемесячный recursive expanding-window forecast;
4. выбирать гиперпараметры только внутри доступной на тот момент истории;
5. сравнить GBRT с expanding historical mean;
6. вычислить итоговый `R2_oos` по формуле статьи и приблизиться к опубликованному значению.

Отрицательный `R2_oos` означает, что на данном варианте реализации GBRT проиграл историческому среднему. Это не доказывает автоматически ошибку кода, но требует проверки alignment, target, периода OOS и процедуры validation.

## Что взято из статьи

- Выборка: `1971-08`–`2018-12`.
- Прогнозы строятся ежемесячно.
- Используется recursive expanding window: история постепенно расширяется.
- Для каждой даты модель переоценивается и строится OOS-прогноз.
- Для GBRT используются неглубокие деревья, число деревьев и learning rate подбираются по validation.
- Benchmark — наивный прогноз на основе исторического среднего excess return.
- OOS `R2` считается так:

```python
R2_oos = 1 - ((actual - prediction) ** 2).sum() / ((actual - benchmark) ** 2).sum()
```

В статье точная сетка GBRT, random seed и полный код не опубликованы. Поэтому значения параметров нельзя считать полностью известными из текста статьи.

## Текущая реализация

### Данные и target alignment

- Модель: `sklearn.ensemble.GradientBoostingRegressor`.
- Признаки: yield/forward-rate переменные, включая `short_rate`, `fwd_2y`–`fwd_10y`.
- Target: `xr_2y`.
- Исходный период macro panel ограничивается `1971-08`–`2018-12`.

Ключевое исправление alignment было сделано так:

```python
yield_only_data = forward_rates.loc[excess_returns.index].copy()
yield_only_data.index = yield_only_data.index + 12
yield_only_data[targets] = excess_returns.to_numpy()
yield_only_data = yield_only_data.dropna().sort_index()
```

После этого target индексируется датой реализации 12-месячного holding-period return. OOS-период начинается с `1990-01`:

```python
oos_start = pd.Period('1990-01', freq='M')
```

Проверка должна дать `1990-01`, `2018-12`, `348` наблюдений.

### Recursive forecast

Для основной noncausal/article-aligned версии используется:

```python
history = data[data.index < forecast_date]
```

Внутри каждой expanding history:

- 85% наблюдений — training;
- 15% — validation;
- лучшая комбинация определяется по validation MSE;
- после выбора параметров модель переобучается на всей доступной history;
- benchmark рассчитывается как expanding historical mean.

Отдельно тестировался causal-вариант:

```python
history = data[data.index <= forecast_date - 12]
```

Он не используется сейчас как основная replication-версия.

## Что показали графики

На большинстве графиков:

- синяя линия `actual` имеет крупные пики и провалы;
- оранжевая линия `prediction` заметно сглажена;
- зелёная линия `benchmark` часто находится рядом с prediction;
- модель плохо ловит резкие развороты excess return.

Это объясняет отрицательный `R2_oos`: даже если корреляция иногда положительная, прогноз не уменьшает среднюю квадратичную ошибку относительно historical mean.

После исправления alignment для текущего прогона было получено:

```text
Полный период: corr=0.0796, n=348
1990-1993:    corr=0.5968, без эпизода=0.0916
2000-2002:    corr=0.5366, без эпизода=0.0508
2007-2009:    corr=0.1735, без эпизода=0.1030
```

Отрицательная глобальная корреляция больше не является основной проблемой. Однако положительная корреляция в отдельных эпизодах ещё не означает положительный `R2_oos`: MSE остаётся немного хуже benchmark.

## Диагностика эпизодов

Использовались:

- корреляция по всему OOS-периоду;
- корреляция внутри эпизодов `1990–1993`, `2000–2002`, `2007–2009`;
- leave-one-episode-out correlation;
- rolling correlation с окном 24 месяца;
- график monthly squared errors для causal и noncausal вариантов.

Эта диагностика нужна, чтобы отличить постоянную проблему модели от нескольких периодов с неправильным прогнозом резкого разворота.

## Поведение grid search

В одном из последних прогонов использовалась сетка:

```python
param_grid = [
    {
        'n_estimators': n,
        'max_depth': depth,
        'learning_rate': rate
    }
    for n in [10, 20, 50, 300, 500]
    for depth in [1, 2]
    for rate in [0.001, 0.002, 0.005, 0.05]
]
```

Чаще всего выбиралась комбинация примерно вида `(10, depth=2, learning_rate=0.001)`. Это практически неагрессивный GBRT, поэтому его прогноз естественно тяготеет к среднему и выглядит как benchmark.

Важно: запись

```python
[0.001, 0.002, 0.005, 0.05, 0,1]
```

в Python означает два отдельных значения `0` и `1`, а не `0.1`. Если требовалось добавить одну десятую, нужно писать `0.1`.

Для следующего controlled-прогона разумна сетка без почти не обучающихся значений:

```python
param_grid = [
    {
        'n_estimators': n,
        'max_depth': depth,
        'learning_rate': rate
    }
    for n in [50, 100, 300, 500]
    for depth in [1, 2, 3]
    for rate in [0.01, 0.03, 0.05, 0.1]
]
```

Это 48 комбинаций. Сетка является проверкой чувствительности, а не точной сеткой статьи: авторы её полностью не публикуют.

## Текущий вывод

После сдвига target на 12 месяцев и получения OOS `n=348` основная архитектура выглядит согласованной с описанием статьи:

- expanding history;
- ежемесячная переоценка;
- отдельная validation-часть внутри history;
- OOS-прогноз на следующую доступную дату;
- historical-mean benchmark;
- `R2_oos` по формуле Campbell–Thompson.

Полностью гарантировать совпадение с авторами пока нельзя, потому что неизвестны точные детали исходного кода: список и трансформация признаков, точная дата первого forecast, правила формирования excess return, гиперпараметры и random seed.

Главное наблюдение: текущая проблема выглядит скорее как слабая предсказательная способность или недообучение GBRT на `xr_2y`, а не как очевидная ошибка только в формуле `R2`. Особенно подозрительно, что validation часто выбирает очень маленькие модели с низким learning rate.

## Конечная цель

Наша конечная цель — не просто получить красивый график или локально лучший validation MSE. Мы хотим:

> полностью повторить кодовую логику статьи для yield-only GBRT, корректно подставить конкретные параметры выбранной модели, воспроизвести recursive OOS-forecast и максимально приблизиться к опубликованному `R2_oos` для `xr_2y`.

После выбора и фиксации окончательной комбинации параметров сетка больше не является итогом исследования: конкретные значения `n_estimators`, `max_depth` и `learning_rate` должны быть подставлены в финальный запуск, а результат нужно сравнить с benchmark, `MSE_GBRT`, `MSE_benchmark`, корреляцией и графиком OOS-прогнозов.

## Новый controlled-прогон: ограничение слишком больших learning rate

После эксперимента с логарифмической сеткой от `0.1` до примерно `0.68` стало понятно, что верхняя часть диапазона learning rate была слишком агрессивной для нашей задачи. Поэтому в следующем прогоне диапазон был ограничен значениями от `0.02` до `0.1`, при этом `n_estimators` и `max_depth` были зафиксированы:

```python

    {
        'n_estimators': 100,
        'max_depth': 3,
        'learning_rate': rate
    }
    for rate in learning_rates
]

print(learning_rates)
```

Фактическая сетка после `[:-1]`:

